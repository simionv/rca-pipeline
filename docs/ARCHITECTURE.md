# RCA Pipeline — Technical Architecture

## Overview

The RCA Pipeline is a Python package (`rca_pipeline`, under `src/`) that classifies support
transcripts with LLMs. It is Excel-driven: one workbook per analysis defines every classification
module, output field and taxonomy code. At build time the workbook is compiled into generated Python
classifiers and taxonomy JSON files; at run time those artefacts are loaded and dispatched concurrently
against the LLM.

Each analysis lives in its own **workspace** folder, `use_cases/<name>/`, with its own definition,
profiles and generated artefacts. The installed console command `rca` operates on one workspace at a
time.

For usage see [manual.md](manual.md); for design rationale see [methodology.md](methodology.md).

### Design principles

- **`src/rca_pipeline/` is the package.** All business logic lives here with relative imports.
  Generated modules import from `rca_pipeline.*` (absolute imports) and are loaded by path, never as
  a library.
- **A use case is a workspace.** Every relative path (definition, profiles, generated, runs) resolves
  from the use-case folder. Building one use case never touches another's artefacts.
- **`generated/` is reproducible but tracked.** Everything in it can be rebuilt with `rca build`, but
  it is committed so a use case can be re-run, reviewed and diffed without rebuilding.
- **Customer data stays out of git.** `data/`, `runs/`, `output/` and `feedback/` in each use case are
  links into a local data archive created by `tools/link_archive.py`.
- **Workflow logic stays in notebooks.** Multi-stage routing, merging and scoring are written per use
  case; the engine classifies one input with a set of modules.

## Workspace resolution

```
rca --workspace use_cases/sd_2026 run …      (or: cd use_cases/sd_2026 && rca run …)
        │
        ├── cli.py: RCA_WORKSPACE = abspath(dir); chdir(dir)        (only with --workspace)
        │           RCA_WORKSPACE defaults to cwd if not already set
        │
        ├── workspace.root() = RCA_WORKSPACE or "."   — read when modules are imported:
        │       config.py   → <ws>/.env, RunConfig path defaults (generated/taxonomies, runs/…)
        │       pipeline.py → <ws>/generated/pipeline_config.json, <ws>/generated/modules/*.py
        │       runner.py   → <ws>/runs/checkpoints, <ws>/definitions (sentinels, staleness)
        │
        └── build.py / validate.py: defaults relative to the current directory
                (definitions/, generated/…, profiles/)
```

Because the package resolves the workspace at import time, `cli.py` sets `RCA_WORKSPACE` **before**
importing any pipeline module. Notebooks change into the use-case folder before importing.

## Data Flow

### Build phase

```
use_cases/<name>/definitions/<definition>.xlsx
    │
    ├── rca validate (run automatically by rca build; stops on errors)
    │
    ├── modules sheet ─┬────────────────────► generated/pipeline_config.json
    ├── fields sheet  ─┘                      (modules, enum validators, list / object-list fields,
    │                                          code fields, output exclusions, enrichment prefixes,
    │                                          column groups)
    │
    ├── modules + fields ───────────────────► generated/modules/<module>.py
    │                                          (written if missing or forced; STALE warning otherwise)
    │
    ├── taxonomy sheet ─────────────────────► generated/taxonomies/<taxonomy_file>.json
    │                                          (rewritten on every build; codes from row order)
    │
    └── per-module SHA-256 hashes ──────────► generated/build_manifest.json
                                               (hashes, timestamps, generator version)
```

At the start of every classification run, `rca run` compares each `definitions/*.xlsx` modification
time with the manifest's `generated_at` and warns `BUILD STALENESS` if a workbook is newer.

### Discovery (optional)

```
rca discover --data tickets.csv
    ├── sample sample_n tickets (seed 42)
    ├── Pass 1: extract category phrases per batch (extract_prompt); merge near-duplicates (≥ 0.75 overlap)
    ├── Pass 2: one call normalises the top_n phrases into a 2-level taxonomy with the module prefix
    └── generated/taxonomies/drafts/<module>_extracted.json, _discovered.json, _draft.json
          → curated by a person into the workbook's taxonomy sheet
```

### Classification phase (`rca run`)

```
rca run --profile profiles/<p>.json
    │
    ├── merge profile into CLI args; set LLM_BACKEND / RCA_MODEL env from --backend / --model
    ├── import pipeline: load generated/pipeline_config.json
    │       └── load generated/modules/*.py via importlib.util.spec_from_file_location
    │             └── MODULE_REGISTRY {module_name → classify_<module>}
    ├── staleness warning; sentinel field per module (from the definition workbook)
    ├── load taxonomies (file list from pipeline_config.json)
    ├── read input CSV/XLSX; drop stale enrichment columns; drop ids on the bad-UID list
    ├── make batches (batch_size, max_chars)            ── --dry-run stops here
    ├── optional: language detection / translation; incremental diff (classify new/changed only)
    ├── optional: load feedback corrections (--feedback-dir); confidence instruction
    ├── load checkpoint; per module, keep batches with any record not yet done
    │
    ├── dispatch every (module, batch) pair concurrently (asyncio semaphore = concurrency)
    │       ├── per task: set prompt suffix (confidence + few-shot) and cost label (contextvars)
    │       └── classify_<module>() or hierarchical L1→L2 → process_batches_async() → call_batch()
    │       └── optional: confidence enrichment; append result to runs/checkpoints/<stem>_checkpoint.jsonl
    │
    ├── merge cached incremental + checkpoint + new results per uid; append failed uids to <stem>_bad_uids.txt
    ├── post_process()  (see below); optional low-confidence flags and review queue
    ├── write output; update incremental state; compact checkpoint; save cost report (if track_costs)
    ├── optional: quality dashboard
    └── optional: gold-set evaluation (--eval-gold-test; skipped with --dry-run)
```

### Library path (`rca_pipeline.pipeline.run_pipeline(cfg)`)

```
run_pipeline_async(cfg)
    ├── optional cost tracker; feedback store (few-shot pools / prompts per module)
    ├── optional confidence instruction
    ├── read input; optional language detection / translation; optional incremental diff
    ├── optional discovery (cfg.mode == "discover")
    ├── for each module, sequentially:
    │       ├── set prompt suffix (confidence + feedback; per-batch for the smart strategy)
    │       ├── hierarchical (L1 → L2) or standard classification
    │       └── optional confidence enrichment
    ├── merge with cached incremental results; update incremental state
    ├── post_process(); optional low-confidence flagging and review queue
    └── write output; cost summary; optional quality dashboard
```

Modules run one after another here; there is no checkpointing on this path. `rca run` instead runs
all modules' batches concurrently and applies the same enhancements per batch (shared helpers
`build_feedback`, `confidence_instruction_for`, `module_suffix` in `pipeline.py`). The prompt suffix
and the cost-attribution label in `llm_client.py` are `contextvars`, so each asyncio task keeps its own
values and concurrent modules never mix few-shot examples or costs.

### Post-processing (`utils.post_process`)

```
merge_results()               join results onto the input by id_col
validate_enum_cols()          blank values outside enum_validators
validate_evidence_fields()    add *_grounded for *_evidence / *_snippet columns (flag, never blank)
derive_labels()               *_code → *_label, *_description; L1 repair + *_class_l1 for "primary" columns
heuristic_fallbacks()         no-op (kept for compatibility)
explode_object_lists()        list-of-object fields → <field>_<key>_<n>
validate_evidence_fields()    again, for evidence columns created by the explosion
explode_lists()               list fields → <field>_1.._N
normalise_friction_columns()  friction_points* → canonical labels (needs friction_categories in config)
derive_positional_labels()    labels for exploded code values
reorder_columns()             original columns first, then by reorder group
drop in_output = FALSE fields
```

## Key Modules

### `cli.py` — the `rca` command

Parses an optional leading `--workspace DIR` / `-w DIR`, sets `RCA_WORKSPACE`, then dispatches:
`validate` → `validate.main`; `build`/`discover`/`promote-drafts` → `build.main` (with
`validate.run` first for `build`); `run` → `runner.main`; `catalog` → `catalog.main`.

### `config.py` — RunConfig + shared loader

Central configuration dataclass. Loads `<workspace>/.env`, then the nearest `.env` above the current
directory, on import. Environment-backed defaults (`RCA_MODEL`, `RCA_TEMPERATURE`, `RCA_MAX_TOKENS`,
`RCA_TIMEOUT`, `RCA_BATCH_SIZE`, `RCA_MAX_CHARS`, `RCA_CONCURRENCY`, `RCA_RETRIES`, …) are evaluated
once at import. Also exports `load_pipeline_config(path=None)`, used by every module to read
`<workspace>/generated/pipeline_config.json`. The full field list is in
[manual section 6](manual.md#6-runconfig-reference).

### `build.py` — Excel compiler

Reads the three data sheets (dropping note rows), filters enabled modules, builds taxonomy JSON from
row order (optional explicit `code` column), generates module source with `generate_module_py()`,
writes `pipeline_config.json` with `build_pipeline_config()` and maintains `build_manifest.json`.
`_GENERATOR_VERSION` (currently 1.7.0) is bumped whenever generated output changes; a mismatch makes
the build recommend `--force-all`.

### `validate.py` — plain-language checks

`check_definition()` and `check_profiles()` return errors and warnings with sheet and Excel row;
`run()` prints them and returns success. Used by `rca validate` and before `rca build`.

### `runner.py` — production runner

Argument parsing and profile merging (`_parse_args`), sentinel detection (`_build_sentinel_map`),
checkpoint load/resume, concurrent dispatch with a live progress table, bad-UID list, checkpoint
compaction, dry-run report, and the optional gold evaluation (`_run_gold_eval`).

### `llm_client.py` — 4-Tier Resilience

```
process_batches_async(batches, system_prompt, user_prompt_template, cfg, parse_fn)
    │   (semaphore = cfg.concurrency; staggered start; optional per-batch prompt suffix)
    └── call_batch()
          ├── Tier 1: tenacity retry  (Retry-After + 1 s, else exponential backoff with jitter 2–90 s;
          │                            a retryable error also pauses all in-flight calls)
          ├── Tier 2: binary split    (invalid JSON on > 2 records; max depth 4)
          ├── Tier 3: single records  (no further degradation; failure → {uid, _error})
          └── Tier 4: UID repair      (re-request uids missing from the response)
```

`robust_json_loads()` strips markdown fences, folds curly quotes, removes trailing commas, extracts
JSON from surrounding prose and salvages complete objects from truncated arrays. The backend is chosen
by `LLM_BACKEND` (`litellm` default, or `openai`) at import.

### `pipeline.py` — Module Registry and library orchestrator

`_build_registry()` loads each generated module with `importlib.util.spec_from_file_location()`, so
`generated/modules/` does not need to be on `sys.path`. Syntax errors in a generated module are logged
and the module is skipped. `run_pipeline()` / `run_pipeline_async()` implement the library path above.

### `utils.py` — pre/post-processing

Batching (`make_batches`), input reading (inserts a synthetic `uid` column if none exists), stale
column removal (`drop_enrichment_cols`, using `_STRUCTURAL_PREFIXES` plus the config's field names),
and the post-processing chain. Friction categories are read from `pipeline_config.json`
(`friction_categories`) at call time; the build does not write that key, so it must be added by hand
or by a notebook.

## Generated Module Format

`rca build` writes one Python file per module to `generated/modules/`. Structure (module with a
taxonomy):

```python
# generated/modules/sd_rc_login.py  (AUTO-GENERATED — do not edit by hand)
from rca_pipeline.config import RunConfig
from rca_pipeline.taxonomy import taxonomy_to_rich_prompt
from rca_pipeline.llm_client import process_batches_async

MODULE_NAME = "sd_rc_login"

def _build_system_prompt(taxonomy_prompt: str) -> str:
    _BEFORE = """You are an expert classifier for Elsevier support tickets.
Your task: <modules.description>

## Taxonomy
"""
    _AFTER = """

## Instructions
1. <prompt_instruction> → `sdli_code`
...
## Output Format
<JSON example from field names and types>

IMPORTANT: Return ONLY valid JSON. ... CRITICAL: Always use LEAF-level codes ..."""
    return _BEFORE + taxonomy_prompt + _AFTER

_USER_PROMPT_TEMPLATE = """Classify the following support transcripts.

{records_json}
..."""

def _validate_record(record): ...          # only when the module has enum: fields

async def classify_sd_rc_login(batches, taxonomies, cfg: RunConfig):
    tax = taxonomies.get("sd_rc_login", {})
    tax_prompt = taxonomy_to_rich_prompt(tax, "SDLI")
    system_prompt = _build_system_prompt(tax_prompt)
    return await process_batches_async(batches, system_prompt, _USER_PROMPT_TEMPLATE, cfg, ...)

def run(batches, taxonomies, cfg): ...      # synchronous wrapper
```

The taxonomy is **not** inlined: it is rendered at run time from `generated/taxonomies/*.json`, so
taxonomy edits take effect after a normal build. The description, instructions and schema **are**
baked in and change only with `rca build --force <module>`. Modules without a taxonomy have a fixed
`_SYSTEM_PROMPT` instead of `_build_system_prompt`.

## Taxonomy Format

Taxonomies are 2-level JSON trees:

```json
{
  "CR1": {
    "label": "Signing in & authentication",
    "description": "optional group description",
    "children": {
      "CR1.1": { "label": "Login blocked",  "description": "Definition: Use when ..." },
      "CR1.2": { "label": "Password reset", "description": "Definition: Use when ..." }
    }
  },
  "CR2": { "...": "..." }
}
```

L1 and L2 nodes have `label` and optionally `description`. Codes are `<PREFIX>n` / `<PREFIX>n.m` from
row order unless the workbook's `code` column pins them. **Adding descriptions to leaf codes is the
single most impactful accuracy improvement.**

## pipeline_config.json Structure

`generated/pipeline_config.json` is the runtime contract between `rca build` and `rca run`. It holds
only the **enabled** modules of the workspace's workbook:

```jsonc
{
  "modules": {
    "contact_reason": {
      "taxonomy_prefix": "CR",
      "taxonomy_file": "contact_reason.json",
      "taxonomy_key": "contact_reason",
      "reorder_group": "contact_reason",
      "reorder_order": 1,
      "description": "...",
      "classify_fn": "classify_contact_reason",
      "code_field": "cr_code",          // first field of type code
      "discovery_mode": "",              // "full" | "extract_only" | ""
      "extract_prompt": ""
    }
  },
  "enrichment_prefixes": [...],   // field names; matching input columns are dropped before a run
  "reorder_groups": {...},        // column ordering in output
  "enum_validators": {...},       // allowed values per enum field (validate_enum = TRUE)
  "list_fields": [...],           // explode_list fields → _1/_2/_3
  "object_list_fields": {...},    // explode_list + explode_keys fields → {field: [keys]}
  "code_fields": [...],           // fields containing taxonomy codes
  "output_exclude": [...]         // in_output = FALSE fields
  // "friction_categories": [...] // optional; not written by the build
}
```

## Notebook Setup

Use-case notebooks walk up from their own location to the use-case folder (the folder containing
`definitions/`), change into it and run stages as subprocesses (`python -m rca_pipeline.cli run …`)
with UTF-8 forced in the child environment. Generic notebooks in `notebooks/` select a use case
explicitly:

```python
WORKSPACE = "scopus_content"   # folder under use_cases/

import os, sys
from pathlib import Path
_root = Path().absolute()
while not (_root / "use_cases").is_dir() and _root.parent != _root:
    _root = _root.parent
_root = _root / "use_cases" / WORKSPACE
os.chdir(_root)                 # before importing rca_pipeline
```

## Testing

Unit tests live in `tests/` and use `pytest`; none call an LLM.

```bash
pytest              # all tests
pytest -x           # stop on first failure
pytest -k validate  # filter by name
```

| Test file | Coverage |
|---|---|
| `tests/test_taxonomy.py` | `flatten_taxonomy`, label/description lookups, `taxonomy_to_rich_prompt`, sort key, code helpers |
| `tests/test_config.py` | `RunConfig` defaults, path correctness, `load_pipeline_config` with real/missing files |
| `tests/test_utils.py` | `drop_enrichment_cols`, `make_batches`, `merge_results`, `validate_enum_cols`, friction normalisation, evidence grounding (quote folding, CJK, fabricated and empty evidence) |
| `tests/test_validate.py` | workbook and profile checks |
| `tests/test_prompt_braces.py` | generated prompts contain no doubled braces |
| `tests/test_smoke_template.py` | copies `use_cases/_template`, then `rca validate`, `rca build` and `rca run --dry-run` |

CI (`.github/workflows/ci.yml`) installs the package, runs `tools/check_repo.py` (also the pre-commit
hook: blocks notebook outputs, e-mail addresses, passwords and large data files) and then `pytest`.

## Dry-run mode

`rca run --dry-run` loads config, taxonomies and input, applies the bad-UID list and batches, then
prints record count, batch plan, sentinel per module, taxonomy status and the enhancements switched on
— with zero LLM calls and no output. It does not read the checkpoint, so it cannot show how many
batches a resume would skip.

```bash
cd use_cases/_template
rca run --profile profiles/example.json --dry-run
```

## Extensibility

### Adding a module

Edit the workspace's definition (rows on `modules`, `fields` and, if it has categories, `taxonomy`),
then `rca validate` and `rca build`. No Python changes needed.

### Adding a use case

Copy `use_cases/_template`, fill in its README, edit the definition, `rca validate`, `rca build`,
`rca run --profile profiles/example.json --dry-run`, then `rca catalog`.

### Adding an enhancement

1. Create `src/rca_pipeline/enhancements/my_enhancement.py`.
2. Add a flag to `RunConfig` in `config.py` (e.g. `enable_my_feature: bool = False`).
3. Call it in `pipeline.py` behind `if cfg.enable_my_feature` (library path).
4. Add a CLI flag in `runner._parse_args()`, add the field to the forwarded `_enhancement_fields`
   list in `runner.run()`, and call it from `runner.run()` too — the runner does not go through
   `pipeline.run_pipeline_async`. Put shared logic in a helper in `pipeline.py` (like
   `module_suffix`) so both paths use the same code, and add a test like
   `tests/test_enhancement_fixes.py::test_rca_run_applies_enhancements`.

### Adding a run profile field

Profiles are merged in `runner._parse_args()`: every key that matches an argparse destination is
applied when the CLI value is still the default; other keys are ignored silently. A new profile field
therefore needs a matching `rca run` flag.

## Version-control strategy

| Path | Status | Reason |
|---|---|---|
| `use_cases/*/definitions/`, `profiles/`, `notebooks/`, `scripts/`, `docs/`, `history/`, `README.md` | tracked | The analysis itself |
| `use_cases/*/generated/` | tracked | Reproducible, but committed so runs can be repeated and reviewed |
| `use_cases/*/data`, `runs`, `output`, `feedback` | ignored (symlinks) | Customer data, kept in the local data archive |
| `use_cases/_template/data/` | tracked | Synthetic sample transcripts |
| `/runs/`, `/output/`, `*.log` | ignored | Stray run output at the repo root |
| `.env` | ignored | Credentials |
| `.venv*/`, `__pycache__/`, build artefacts, `~$*` Excel lock files, `.ipynb_checkpoints/` | ignored | Local state |
