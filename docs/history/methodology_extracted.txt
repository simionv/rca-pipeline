RCA Pipeline
Methodology Deep-Dive
LLM-Powered Classification for Support Transcripts
Version 3.0  —  May 2026
CONFIDENTIAL
1. Introduction
The RCA Pipeline is an LLM-powered classification system designed to enrich support transcripts with structured metadata. It takes raw customer support conversations (in CSV or XLSX format) and produces a richly annotated output across 19 classification modules covering contact reason, root cause, customer effort, sentiment, agent performance, communication effectiveness, voice of customer, escalation, resolution quality and actions, follow-up, compliance and risk, insights and opportunities, customer profile, knowledge management, interaction classification, containment and deflection, customer journey, and customer intent.
Every classification is backed by taxonomy codes (for the 10 taxonomy-backed modules), evidence quotes, and enum-validated structured fields. This document describes the methodology: how the pipeline classifies, why each design decision was made, what trade-offs were accepted, and what guarantees the system provides. It is intended for data scientists, quality analysts, and engineering stakeholders who need to understand the system at a technical level.
1.1 Design Principles
The pipeline is built around five core principles that shape every design decision:
Single source of truth. All 19 module definitions, their fields, taxonomy codes, and prompt instructions live in one Excel workbook. There is no separate configuration to drift out of sync. The build step generates everything else from this single file.
Taxonomy-first classification. Every taxonomy-backed classification is anchored to a curated, human-reviewed taxonomy with exactly two levels (L1 group, L2 leaf). The LLM selects from this closed set rather than inventing free-text categories, ensuring consistency across runs and analysts.
Evidence-grounded outputs. For modules requiring interpretation (root cause, customer effort, agent performance, voice of customer, compliance and risk), the LLM is required to provide a verbatim evidence quote from the transcript. This makes every classification auditable.
Resilience over speed. The 4-tier resilience chain (retry, split, single, UID-repair) ensures that transient API failures, malformed responses, and edge-case transcripts produce stubbed errors rather than crashes. Every record gets an output, even if it is an error stub.
Opt-in complexity. The seven enhancement modules (confidence scoring, feedback loop, hierarchical classification, incremental processing, cost tracking, language detection, quality dashboard) are all disabled by default. Enabling them requires a single boolean flag. The core pipeline behaves identically without any enhancements active.
1.2 Scope
This methodology applies to the classification phase of the pipeline. It does not cover the build phase (build_pipeline.py), the Excel workbook design, or the infrastructure layer (Azure deployment, VNet configuration, credential management). Those are covered in the companion Manual document.
2. Classification Approach
2.1 Overview
Each transcript passes through all 19 classification modules running concurrently. Every module receives the full transcript text and — where applicable — its taxonomy, and returns structured JSON with the assigned codes, descriptions, evidence, and metadata fields. The modules operate independently: the contact reason classifier does not see the root cause result, and vice versa. This prevents error propagation between modules.
The 19 modules are organised into seven groups: Core (contact_reason, interaction_classification), Why & Intent (root_cause, customer_intent), Customer Experience (customer_sentiment, customer_effort, voice_of_customer, customer_journey), Agent & Comms (agent_performance, communication_effectiveness), Resolution & Follow-up (resolution_quality, resolution_actions, escalation, follow_up), Self-Service & Knowledge (containment_and_deflection, knowledge_management, insights_and_opportunities), and Risk & Profile (compliance_and_risk, customer_profile).
2.2 Module Architecture
A module is defined by three things in the Excel workbook: a row on the modules sheet (name, prefix, taxonomy file, description), rows on the fields sheet (output field names, types, and prompt instructions), and — for taxonomy-backed modules — rows on the taxonomy sheet (L1/L2 codes with labels and descriptions). The build step reads these and generates a Python file containing the system prompt, user prompt template, output schema, and the classify function.
The generated system prompt has a fixed structure. It begins with a role statement, followed by the task description from the modules sheet, the full taxonomy in a rich format (code, label, description for each node) where applicable, the field-by-field instructions from the fields sheet, the expected JSON output schema, and critical instructions about using leaf codes and returning valid JSON.
Ten modules have taxonomies: contact_reason (CR), root_cause (RC), customer_effort (CE), agent_performance (AP), voice_of_customer (VOC), resolution_actions (RA), follow_up (FU), compliance_and_risk (RISK), knowledge_management (KM), and customer_intent (INT). The remaining nine modules use enum fields, boolean fields, and free-text fields, with prompt instructions guiding classification directly without a taxonomy.
2.3 Prompt Engineering
The prompt_instruction column on the fields sheet is the single most impactful lever for classification accuracy. Each instruction is a directive sentence telling the LLM exactly what to produce for that field. Instructions are baked verbatim into the system prompt at build time.
For code fields, the instruction directs the LLM to assign the most specific leaf-level taxonomy code, matching on meaning rather than keywords, and using the description to decide. For evidence fields, the instruction uses copy-verbatim language to minimise fabrication: instructions like "Copy verbatim the single most relevant sentence or phrase from the transcript. Do NOT paraphrase, infer, or add words that are not in the transcript." For enum fields, the allowed values and their precise definitions are included directly in the instruction.
The output schema is presented as a JSON template with placeholder values showing the expected type for each field. The LLM sees this exact structure and mirrors it in its response. The schema includes the uid field first, ensuring every response can be matched back to the input record.
2.4 Batching Strategy
Transcripts are grouped into batches before being sent to the LLM. Each batch contains multiple transcripts in a single API call, which amortises the system prompt tokens across many records and significantly reduces cost and latency. Batch boundaries are controlled by two parameters: batch_size (maximum number of records per batch, default 10) and max_chars_per_batch (maximum total character length of all transcripts in a batch, default 60,000). Whichever limit is reached first triggers a new batch.
The character limit prevents extremely long transcripts from causing token overflow. A single 50,000-character transcript will be placed alone in its own batch, while ten 2,000-character transcripts will be grouped together. This adaptive batching ensures efficient token utilisation regardless of transcript length distribution.
2.5 Temperature and Determinism
The default temperature is 0.0, which produces near-deterministic outputs. This means the same transcript classified twice should receive the same code. In practice, exact determinism is not guaranteed by LLM providers (implementation details like batching, quantisation, and infrastructure changes can cause minor variations), but temperature 0 minimises run-to-run variance.
For discovery mode, where the goal is to extract diverse categories from transcripts, a slightly higher temperature (0.2–0.3) may be appropriate. This is configurable via the temperature parameter.
3. Taxonomy Design
3.1 Two-Level Hierarchy
Every taxonomy uses exactly two levels of hierarchy. L1 codes represent broad categories (e.g., "Technical & platform issues", "Product or software defect"). L2 codes represent specific leaf-level issues within each L1 group (e.g., "Login or authentication failure", "Regression from a recent release"). Codes are assigned by row order in the Excel sheet and use a prefix followed by a number and dot notation: CR1, CR1.1, CR1.2, CR2, CR2.1, etc.
The two-level constraint is deliberate. Deeper hierarchies (three or more levels) increase the LLM's decision space exponentially and degrade leaf-level accuracy. Two levels provide enough granularity for operational reporting while keeping the decision space manageable. If finer granularity is needed, the recommended approach is to split an L1 group into multiple L1 groups rather than adding an L3 level.

3.2 Descriptions as Classification Anchors
Adding detailed descriptions to L2 leaf codes is the single most effective accuracy improvement available to taxonomy designers. The description field tells the LLM exactly what a code means, including boundary conditions, examples, and associated signals. Without descriptions, the LLM must infer the scope of each code from its label alone. Labels are often ambiguous: "Login or authentication failure" could mean a password issue, an MFA problem, an SSO failure, or an account lock. The description disambiguates by listing the specific scenarios that fall under each code.
3.3 Catch-All Codes
Every L1 group in every taxonomy includes an "Other" leaf code (e.g., "Other technical issue", "Other billing issue"). This ensures the LLM always has a valid code to assign, even for edge cases that don't fit the defined leaves. The alternative—forcing the LLM to pick the closest imperfect match—introduces systematic misclassification of edge cases.
If the "Other" code for a group accumulates more than 10–15% of assignments, this signals that the group's taxonomy needs refinement: the edge cases likely represent one or more distinct categories that should be broken out as new L2 codes.
3.4 Taxonomy Discovery (Cold-Start)
When no taxonomy exists, the discovery module extracts one from the data using a two-pass process. Pass 1 (extraction) sends batches of transcripts to the LLM with instructions to identify abstract category phrases. A pre-deduplication step collapses near-duplicates using token overlap before sending to Pass 2. Pass 2 (normalisation) takes the top-N frequency items and asks the LLM to organise them into a structured two-level taxonomy with the correct code prefix.
The discovered taxonomy is written to a draft directory for human review. It is never used directly for classification without editorial oversight. The human reviewer merges duplicates, renames labels, adds descriptions, and removes noise before promoting the draft to a live taxonomy file.
4. Resilience Architecture
4.1 Four-Tier Resilience Chain
Every LLM call flows through a four-tier resilience chain that handles transient failures, malformed responses, and edge-case transcripts without crashing the pipeline.
The tiers cascade: a batch that fails at Tier 1 (all retries exhausted due to a malformed JSON response) is sent to Tier 2 (split). Each half is processed independently. If a half still fails, it cascades to Tier 3 (single-record processing). If even a single record fails at Tier 3, it is stubbed with an error dict containing the uid and an _error field. This guarantees that every input record produces an output, even if that output is an error stub.
4.2 Robust JSON Parsing
The robust_json_loads() function handles the many ways LLM output can deviate from strict JSON. It strips markdown code fences, replaces smart quotes with straight quotes, removes trailing commas before closing brackets, extracts embedded JSON from surrounding prose, handles single-quoted strings, and attempts to repair truncated responses by closing open brackets and extracting partial records.
Truncated response repair is particularly important for long batches and modules with many output fields (such as customer_journey and customer_intent, which each have 10+ fields). If the LLM runs out of max_tokens mid-response, the parser truncates at the last complete key-value pair, closes the open braces, and salvages however many complete records were present.
4.3 Crash Recovery and Checkpointing
The production runner (run_pipeline.py) writes results to an append-only JSONL checkpoint file after each batch completes. If the process crashes or is interrupted, re-running the same command automatically resumes from where it left off. Each module has a sentinel field (the first code or boolean field defined for that module) that determines whether a UID is "done" for that module. A UID is only skipped if its sentinel field is present and non-empty in the checkpoint.
After a successful run, the checkpoint is compacted (deduplicated by UID) and UIDs that produced errors are appended to a persistent bad-UIDs file. On subsequent runs, bad UIDs are excluded from the input to avoid re-processing known failures. The bad-UIDs file can be edited manually to retry previously failed records.
5. Quality Controls
5.1 Evidence Hallucination Detection
After classification, every column matching *_evidence* or *_snippet* is validated against the source transcript. The validation uses a two-tier approach. Tier 1 checks for an exact substring match after whitespace normalisation. Tier 2 checks token overlap: if at least 65% of the evidence's word tokens appear in the transcript, the evidence is considered grounded.
For each evidence column, a boolean *_grounded column is added (e.g., root_cause_evidence_grounded, contact_reason_evidence_grounded). Ungrounded evidence is logged with a warning but not blanked, allowing human reviewers to see the hallucinated text and decide how to handle it.
5.2 Enum Validation
Fields with constrained value sets are validated post-classification. Values are normalised to lowercase and compared against the allowed set. Invalid values are set to blank and logged with a warning. This catches LLM outputs like "Resolved" (wrong case), "partially resolved" (not in set), or "escalation" (wrong form). The pipeline defines enum fields across most modules, covering fields such as sentiment_label, effort_score, resolution_status, escalation_reason, risk_severity, and customer_type.
5.3 L1 Code Correction
The LLM occasionally returns an L1 group code (e.g., CR4) instead of a leaf code (e.g., CR4.1) in a primary_code field. Post-processing detects these (codes without a dot) and attempts to resolve them. If the L1 group has exactly one child, the code is replaced with that child. If it has multiple children, the L1 code is kept and a warning is logged. Increasing the specificity of L2 descriptions reduces the frequency of this issue.
5.4 Confidence Scoring (Enhancement 1)
When enabled, the pipeline appends a confidence instruction to every system prompt, asking the LLM to include a confidence float (0.0–1.0) in each result object. The instruction provides calibration guidance: 0.9–1.0 for clear matches, 0.7–0.9 for good matches with minor ambiguity, 0.5–0.7 for moderate ambiguity, and 0.0–0.5 for guesses on ambiguous or sparse transcripts.
Records below the configured threshold (default 0.70) are flagged with _needs_review = True and can be exported to a separate review queue spreadsheet. When the API supports logprobs (token log-probabilities), these provide a more reliable confidence signal than self-reporting: the geometric mean of token probabilities for the classification code tokens gives an objective measure of the model's certainty.
5.5 Quality Dashboard (Enhancement 7)
The automated quality dashboard generates a structured report after each classification run, covering coverage per module (percentage of non-empty codes), code distribution with alerts for codes at less than 1% or greater than 50% usage, evidence grounding rates, error rates and breakdowns, confidence distributions, language distributions, anomaly detection (L1-only codes, mode collapse, duplicate UIDs), and run-over-run comparison if a previous report is provided.
The dashboard outputs both a machine-readable JSON file (for CI/CD gating or automated alerting) and a human-readable Excel workbook with separate sheets for summary, coverage, code distribution, and anomalies.
6. Human-in-the-Loop Feedback
6.1 Feedback Store (Enhancement 2)
The feedback mechanism allows human reviewers to correct misclassified records. Each correction is stored in an append-only JSONL file (one per module) containing the record UID, a truncated transcript, the original LLM classification, the corrected classification, an optional reason note, and a timestamp. Corrections are deduplicated by UID at read time (latest correction wins).
On subsequent runs, the pipeline builds a few-shot prompt block from stored corrections and appends it to every system prompt for the relevant module. The LLM sees concrete examples of "WRONG classification" versus "CORRECT classification" with the reviewer's reasoning, anchoring its behaviour on ambiguous cases that previously caused errors.
6.2 Selection Strategies
Four strategies control which corrections are selected for few-shot injection. The "recent" strategy selects the most recently added corrections, ensuring the newest reviewer judgements take priority. The "diverse" strategy selects one example per distinct corrected code, maximising taxonomy coverage. The "frequent" strategy selects the most commonly corrected original-to-corrected pairs, catching systematic LLM errors. The "smart" strategy is a two-stage adaptive approach described below — it is the recommended choice once 10 or more corrections exist across multiple codes.
A total size cap (default 4,000 characters) prevents the few-shot block from consuming excessive context window. The pipeline stops adding examples once the cap is reached, even if max_examples has not been reached.
6.2.1 The "smart" Adaptive Strategy
The "smart" strategy addresses three limitations of static approaches: irrelevant examples (a contact reason correction injected into a root cause batch confuses the model), wasted slots (multiple corrections for the same code fill the prompt with near-identical examples), and poor representative selection (longer transcripts are not always more informative). It operates in two stages:
Stage 1 — Content-Aware Pool Building
At startup, corrections are grouped by corrected taxonomy code. Within each group, the correction with the highest stage1_score is selected as the group representative. The result is a candidate pool — one entry per distinct corrected code — held in memory for the duration of the run.
Each correction is scored by three signals: has_reason (weight 0.4, whether the reviewer left an explanatory note), content_score (weight 0.3, rewards varied and substantive transcripts), and recency (weight 0.3, timestamp normalised to 0–1 over the module's correction history).
content_score = (unique_tokens / total_tokens) × (min(unique_tokens, 80) / 80)
score = 0.4 × has_reason  +  0.3 × content_score  +  0.3 × recency
Stage 2 — Per-Batch Jaccard Reranking
Before each batch's LLM call, Stage 2 reranks the pool by Jaccard token-overlap against the batch's transcripts. The maximum overlap across all records in the batch is used (not mean), so a single strongly-matching record is sufficient to surface the example. Pool entries are sorted by stage2_score descending, with stage1_score as tie-breaker. Different batches in the same run therefore receive different few-shot examples tailored to their content.
stage2_score(correction, batch) = max over records in batch of: |tokens(correction) ∩ tokens(record)| / max(|tokens(correction)|, |tokens(record)|)
6.3 Correction Import
Corrections can be imported from a reviewed spreadsheet. The expected format is the enriched output with additional *_corrected columns (e.g., contact_reason_primary_code_corrected) for rows where the reviewer changed the value. An optional correction_reason column provides the reviewer's note. The import function auto-detects corrected columns, compares values, and stores only rows where the corrected value differs from the original.
7. Hierarchical Classification (Enhancement 3)
The standard classification approach asks the LLM to select a leaf code from the full taxonomy in a single step. For taxonomies with many L2 codes (e.g., contact_reason with 40+ leaves across 9 L1 groups, or root_cause with 30+ leaves across 8 L1 groups), the decision space may be too large for reliable leaf-level accuracy.
The hierarchical approach splits classification into two steps. Step 1 presents only the L1 groups (with child counts and descriptions) and asks the LLM to select the best-fitting group. Step 2 presents only the L2 leaves within the selected group and asks for the specific leaf code. Each step sees a much smaller decision space, which may improve accuracy at the cost of doubling LLM calls.
Both steps request a confidence score. The joint confidence is computed as the product of the L1 and L2 confidences (reflecting that both decisions must be correct for the final classification to be correct). If the L2 step fails, the pipeline falls back to the L1 code. Step 2 runs all L1 groups concurrently, so wall-clock time is dominated by the slower step, not their sum.
The hierarchical approach is configured per-module via the hierarchical_modules list in RunConfig. Modules not listed use the standard single-step approach. This allows mixing: for example, contact_reason (9 L1 groups, 40+ L2 leaves) and root_cause (8 L1 groups, 30+ L2 leaves) are strong candidates for hierarchical mode, while customer_effort (3 L1 groups) is well-suited to standard classification.
8. Incremental Processing (Enhancement 4)
For production environments where new transcripts arrive daily, re-classifying the entire dataset on each run is wasteful. The incremental processing module maintains a state database (JSONL) that tracks every previously classified record by UID and a hash of its transcript text. On each run, the module compares the incoming data against the state to identify three categories: new records (UID not in state), changed records (UID in state but text hash differs), and unchanged records (UID in state with matching text hash).
Only new and changed records are dispatched to the LLM. Cached results for unchanged records are retrieved from the state and merged into the final output. Stale records (UIDs in state but no longer in the current dataset) are pruned from the state file. After classification, the state is updated with the new results and persisted to disk.
The text hash uses SHA-256 on whitespace-normalised, lowercased text, truncated to 16 hex characters. This detects meaningful content changes while ignoring formatting differences.
9. Cost Tracking (Enhancement 5)
The cost tracker records token usage from every LLM API call and computes estimated USD costs using a built-in pricing table. The tracker is registered globally before classification begins; after each successful LLM call, the response's usage field (prompt_tokens, completion_tokens) is extracted and recorded against the current module label.
The cost report provides per-module breakdowns (total calls, total records, total tokens, total cost, average cost per record, average tokens per record, retry count, throughput), overall totals, and cost estimates for future runs based on historical averages.
Cost data enables operational decisions: modules with few output fields (e.g., escalation, interaction_classification) can be batched more aggressively. Modules with many output fields and evidence requirements (e.g., agent_performance with 9 fields, customer_journey with 11 fields) may benefit from smaller batches or a two-pass approach with a cheaper model for initial screening. Running all 19 modules against large datasets is the primary cost driver; the --modules flag allows selectively running only the modules needed for a given use case.
10. Multi-Language Support (Enhancement 6)
The language module provides detection and optional translation for non-English transcripts. Detection uses a heuristic word-frequency approach: for each transcript, the proportion of words matching common-word sets for English, Spanish, French, German, and Portuguese is computed, and the highest-scoring language is selected. If the langdetect library is installed, it is used instead for broader coverage including CJK and Arabic scripts.
Three strategies are available for handling non-English text. The "translate" strategy translates non-English transcripts to English via the LLM before classification. This produces the most accurate results because the taxonomy, prompt instructions, and classification are all in English. The "prompt" strategy keeps the original text but modifies the system prompt to instruct the LLM that the transcript is in a specific language and that all output fields should be in English. The "detect" strategy only adds language metadata columns without modifying the text or prompts.
Language metadata columns (_detected_language, _language_confidence) are always added to the output when detection is enabled. If translation was performed, _original_text and _translated_from columns preserve the original text. The customer_profile module also captures a detected_language field independently as part of its structured output.
11. Strengths and Limitations
11.1 Strengths
Comprehensive analytical coverage. With 19 modules producing 140+ output fields per record, the pipeline provides a complete analytical view of a support interaction — from the customer’s reason for contact through to root cause, resolution quality, agent performance, compliance risk, and strategic insights — in a single pass.
Accuracy on well-defined taxonomies. When L2 descriptions are detailed and unambiguous, classification accuracy is high. The LLM matches on meaning rather than keywords, handling paraphrasing, synonym variation, and multi-language input within the same taxonomy.
Auditability. Every classification includes evidence quotes and justification chains. The quality dashboard and confidence scoring provide aggregate and per-record quality signals. The feedback store creates a traceable record of human corrections.
Operational efficiency. Incremental processing, checkpointing, and cost tracking support production workloads with thousands of daily transcripts. The pipeline handles crashes gracefully and can resume without reprocessing.
Extensibility. New modules are added by editing a single Excel workbook and running the build step. No code changes are needed. The enhancement modules are composable and independently toggleable. Use-case-specific deployments can activate only the modules relevant to their analytical needs.
11.2 Limitations
LLM dependency. Classification quality is bounded by the LLM’s capabilities. Extremely long transcripts may be truncated by the model’s context window. Ambiguous transcripts may receive different codes on different runs (even at temperature 0, provider-side non-determinism exists).
Taxonomy design is critical. A poorly designed taxonomy (vague labels, missing descriptions, overlapping codes) will produce poor results regardless of the LLM’s capability. The pipeline cannot compensate for ambiguous taxonomy design.
No cross-module reasoning. Each module classifies independently. The root cause classifier does not know the contact reason, the resolution classifier does not know the escalation outcome. This prevents error cascading but also prevents beneficial context sharing between related modules.
Cost at scale. Each record is processed by each active module in a separate LLM call. For all 19 modules across 100,000 transcripts, this is approximately 190,000 module-record pairs, batched into roughly 19,000 API calls. At typical GPT-4o pricing, this costs approximately $600–$1,000 depending on transcript length and field complexity. The --modules flag allows limiting runs to only the modules required, and the cost tracker enables precise monitoring.
Inference vs. evidence. Several modules (customer_profile, insights_and_opportunities, containment_and_deflection) require inference rather than direct extraction. These are inherently less verifiable than taxonomy-grounded modules. The prompt instructions include anti-inference guards where appropriate, but some degree of LLM judgement is unavoidable.
12. Data Privacy Considerations
Transcript text is sent to an LLM provider (Azure OpenAI or OpenAI) for classification. The data processing agreement with the provider governs how this data is handled. When using Azure OpenAI with a private endpoint (VNet deployment), transcript data does not traverse the public internet.
The pipeline stores transcript text in several locations: the input file, the checkpoint JSONL, the output file, and (if feedback is enabled) the feedback correction files. The feedback store truncates transcript text to 1,500 characters by default to minimise data exposure. The incremental state file stores only a hash of the transcript text, not the text itself.
Classification codes, enum values, quality reports, and cost reports do not contain transcript text and can be shared more freely. The review queue export contains full transcript text and should be handled with the same care as the original input data. The customer_profile module infers personal characteristics (customer type, technical sophistication, communication style) from transcript signals — these inferences should be treated as sensitive personal data under applicable privacy regulations.
