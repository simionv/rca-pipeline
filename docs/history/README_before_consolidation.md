# RCA Pipeline

**LLM-powered Root Cause Analysis pipeline for classifying support transcripts.**

Takes raw support transcripts (CSV/XLSX) and enriches each record with structured classifications — contact reason, root cause, resolution status, escalation detection, troubleshooting steps, and more — all driven by a single Excel workbook definition.

---

## Quick Start

```bash
# 1. Install dependencies (uv recommended)
uv sync
# or: pip install -e .

# 2. Set up credentials
cp .env.example .env
# Edit .env with your Azure OpenAI / OpenAI credentials

# 3. Build the pipeline from the Excel definition
python build_pipeline.py build --input definitions/pipeline_definition.xlsx

# 4. Run classification
python run_pipeline.py --input data/transcripts.csv --text-col conversation
```

Or use a **run profile** for repeatable runs:

```bash
python run_pipeline.py --profile profiles/scopus_content_profile.json
```

## How It Works

```
definitions/pipeline_definition.xlsx     (you define modules, fields, taxonomy)
         │
         ▼
  build_pipeline.py build                (generates classifiers, taxonomy JSONs, config)
         │
         ├─► generated/modules/          (auto-generated Python classifiers)
         ├─► generated/taxonomies/       (taxonomy JSON files)
         └─► generated/pipeline_config.json
         │
         ▼
  run_pipeline.py --profile ...          (classifies transcripts with LLM)
         │
         ▼
  runs/output/enriched_output.xlsx       (original data + classification columns)
```

The pipeline has three phases:

1. **Build** — Reads the Excel definition and generates taxonomy JSON files, per-module Python classifiers, and `generated/pipeline_config.json`.
2. **Discovery** *(optional)* — If no taxonomy exists yet, the LLM extracts a draft taxonomy from a sample of your data.
3. **Classification** — Dispatches concurrent LLM calls across all modules, post-processes results (label derivation, enum validation, list explosion), and writes the enriched output.

## The Pipeline Definition Excel

Everything is defined in one Excel workbook with three data sheets:

### Modules Sheet
Each row defines a classification module:

| Column | Description |
|--------|-------------|
| `module_name` | Python identifier (e.g. `contact_reason`) |
| `taxonomy_prefix` | Code prefix (CR, RC, RS, TS). Blank for no-taxonomy modules. |
| `taxonomy_file` | Output JSON filename |
| `enabled` | TRUE/FALSE toggle |
| `description` | Task description baked into the LLM system prompt |

### Fields Sheet
Each row defines an output field. **`prompt_instruction` is the most impactful column — it directly drives LLM accuracy.**

| Column | Description |
|--------|-------------|
| `field_name` | Output column name |
| `field_type` | `code`, `str`, `bool`, `int`, `float`, `list`, `enum:val1,val2,...` |
| `prompt_instruction` | Exact instruction sent to the LLM |
| `in_output` | FALSE to strip from final output |
| `explode_list` | TRUE to expand lists into `_1`, `_2`, `_3` columns |
| `validate_enum` | TRUE to enforce allowed values |

### Taxonomy Sheet
Defines 2-level classification codes. **Codes are auto-assigned by row order — do not type codes manually.**

| Column | Description |
|--------|-------------|
| `level` | `L1` (group) or `L2` (leaf) |
| `label` | Category name |
| `description` | Detailed description — adding good L2 descriptions is the single best accuracy improvement |

## Key Commands

### Build

```bash
# Normal build (only regenerates what changed)
python build_pipeline.py build --input definitions/pipeline_definition.xlsx

# Force-regenerate specific modules
python build_pipeline.py build --input definitions/pipeline_definition.xlsx --force contact_reason root_cause

python build_pipeline.py build --input definitions/pipeline_definition.xlsx --dry-run
```

### Discovery (no taxonomy yet)

```bash
# Run discovery to create starter taxonomies from raw data
python build_pipeline.py discover \
    --input definitions/pipeline_definition.xlsx \
    --data data/transcripts.csv \
    --modules contact_reason root_cause \
    --sample-n 100

# Review drafts in generated/taxonomies/, then promote
python build_pipeline.py promote-drafts --input definitions/pipeline_definition.xlsx
```

### Classification

```bash
# Preview what would run (dry-run — no LLM calls)
python run_pipeline.py --profile profiles/scopus_content_profile.json --dry-run

# With profile (recommended for production)
python run_pipeline.py --profile profiles/scopus_content_profile.json

# Without profile
python run_pipeline.py \
    --input data/transcripts.csv \
    --text-col conversation \
    --batch-size 12 \
    --concurrency 4

# Background run (survives terminal close)
nohup python run_pipeline.py --profile profiles/scopus_content_profile.json > console.log 2>&1 &

# Watch log output
tail -f run_pipeline.log
```

### Adding a New Module

1. Add a row to the **modules** sheet
2. Add field rows to the **fields** sheet (with `prompt_instruction` for each)
3. Add L1/L2 rows to the **taxonomy** sheet (if applicable)
4. `python build_pipeline.py build --input definitions/pipeline_definition.xlsx`
5. The new module is automatically registered and will run on next classification

## Enhancement Modules

Seven optional enhancement modules live in `rca_pipeline/enhancements/`. All are opt-in via `RunConfig` flags or CLI arguments.

### 1. Confidence Scoring (`enhancements/confidence.py`)

Adds a confidence score to each classification. Low-confidence records are flagged for human review.

```json
{ "enable_confidence": true, "confidence_threshold": 0.70, "export_review_queue": true }
```

**How it works:** The LLM is asked to self-report confidence (0–1) as an additional JSON field. When logprobs are available from the API, token-level probabilities provide a more reliable signal. Records below the threshold get `_needs_review = True`.

**Output columns:** `_confidence`, `_needs_review`

### 2. Human-in-the-Loop Feedback (`enhancements/feedback.py`)

Stores human corrections and injects them as few-shot examples in future prompts.

```python
from rca_pipeline.enhancements.feedback import FeedbackStore

store = FeedbackStore("runs/feedback/")
store.add_correction("contact_reason", uid="42", text="...",
    original={"contact_reason_primary_code": "CR1.2"},
    corrected={"contact_reason_primary_code": "CR3.1"},
    reason="This is a password issue, not login blocked")

# Import corrections from a reviewed spreadsheet
store.import_from_review_file("runs/output/reviewed.xlsx", module="contact_reason")
```

**Selection strategies:**

| Strategy | Description | Best used when |
|---|---|---|
| `recent` | Most recent N corrections | Corrections are always up to date |
| `diverse` | One per distinct corrected code | Maximising taxonomy coverage |
| `frequent` | Most commonly corrected pairs | Catching systematic LLM errors |
| `smart` | **Two-stage adaptive selection** (recommended) | 10+ corrections across multiple codes |

**`smart` strategy:** Stage 1 scores each correction with `0.4 × has_reason + 0.3 × content_score + 0.3 × recency`, keeping the best representative per corrected code. Stage 2 reranks by Jaccard token-overlap with the current batch's transcripts — no embeddings, no extra API calls.

**Storage:** `runs/feedback/<module>_corrections.jsonl` — append-only, deduplicated at read time.

### 3. Hierarchical Classification (`enhancements/hierarchical.py`)

Two-step L1→L2 classification that narrows the decision space for each step.

```json
{ "hierarchical_modules": ["contact_reason", "root_cause"] }
```

Step 1 classifies the L1 group (small decision space), Step 2 classifies the L2 leaf within that group. Doubles LLM calls but improves leaf-level accuracy on large taxonomies.

### 4. Incremental Processing (`enhancements/incremental.py`)

Process only new or changed records instead of re-classifying the entire dataset.

```json
{ "incremental": true, "incremental_state_file": "data/state.jsonl" }
```

Detects new, changed, and deleted records via UID + text-hash comparison. Cached results are merged into the output for unchanged records.

### 5. Cost Tracking (`enhancements/cost_tracker.py`)

Tracks token usage and estimated cost per record, per module.

```json
{ "track_costs": true, "cost_report_dir": "runs/cost_reports" }
```

**Output:** `runs/cost_reports/costs_<timestamp>.json` — per-module breakdown, cost per record, throughput metrics, and batch-size recommendations.

### 6. Multi-Language Support (`enhancements/language.py`)

Language detection and optional translation for non-English transcripts.

```json
{ "detect_language": true, "language_strategy": "translate" }
```

**Strategies:** `translate` (translate to English before classification), `prompt` (keep original, adapt prompts), `detect` (metadata only).

**Output columns:** `_detected_language`, `_language_confidence`, `_original_text` (if translated)

### 7. Quality Dashboard (`enhancements/quality_dashboard.py`)

Automated quality report after each classification run.

```json
{ "run_quality_check": true, "quality_report_dir": "runs/output" }
```

**Report includes:** coverage per module, code distribution alerts, evidence grounding rates, error rate, confidence distribution, anomaly detection (L1-only codes, mode collapse, duplicate UIDs), run-over-run comparison.

**Output:** `quality_report.json` + `quality_report.xlsx`

### LLM Backend

The pipeline supports two backends, switchable without code changes.

| Backend | Library | Model string format | Best for |
|---------|---------|-------------------|----------|
| `litellm` | LiteLLM | `azure/deployment-name` | Multi-provider (Azure, OpenAI, Anthropic, etc.) |
| `openai` | openai SDK | `deployment-name` (no prefix) | Direct Azure/OpenAI |

**Four ways to set backend** (highest priority wins):

```bash
# 1. CLI flag
python run_pipeline.py --backend openai --model dsaic-llm-general

# 2. Run profile JSON: "backend": "openai", "model": "dsaic-llm-general"

# 3. .env: LLM_BACKEND=openai, RCA_MODEL=dsaic-llm-general

# 4. Default in llm_client.py (lowest priority)
```

## LLM Resilience

Every LLM call goes through a 4-tier resilience chain:

1. **Tier 1 — Retry**: Exponential backoff on transient errors (rate limits, timeouts)
2. **Tier 2 — Split**: Binary-split the batch and retry each half (batch > 2 records)
3. **Tier 3 — Single**: Process each record individually (batch ≤ 2 records)
4. **Tier 4 — UID Repair**: Re-request any UIDs missing from the LLM response

The `robust_json_loads()` parser handles: markdown fences, smart quotes, trailing commas, embedded JSON, single quotes, and truncated responses.

---

## Crash Recovery

The runner uses JSONL checkpointing with automatic resume:

- Results are appended to `runs/checkpoints/<input>_checkpoint.jsonl` after each batch
- On restart, the checkpoint is loaded and only outstanding batches are dispatched
- Each module has a **sentinel field** — a UID is "done" for a module only if its sentinel is present
- After a successful run, the checkpoint is compacted (deduplicated)

**To resume after a crash:** just re-run the same command — no flags needed.

**To start fresh:** delete the checkpoint and bad-UIDs files:

```bash
# Windows
del runs\checkpoints\*_checkpoint.jsonl runs\checkpoints\*_bad_uids.txt

# Linux/Mac
rm runs/checkpoints/*_checkpoint.jsonl runs/checkpoints/*_bad_uids.txt
```

## Quality Controls

### Evidence Hallucination Detection

After classification, every column matching `*_evidence*` or `*_snippet*` is validated against the source transcript using two tiers:

1. **Exact match** — substring match after whitespace normalisation
2. **Token-overlap** — if ≥65% of evidence tokens appear in the transcript, it's considered grounded

A boolean `*_grounded` column is added for each evidence field (e.g. `root_cause_evidence_grounded`). Ungrounded evidence is logged but not blanked — visible for review.

### Anti-Hallucination Prompt Design

Evidence fields use "copy verbatim" instructions:
```
Copy verbatim the single most relevant sentence or phrase from the transcript.
Do NOT paraphrase, infer, or add words that are not in the transcript.
```

> After updating prompt instructions, rebuild: `python build_pipeline.py build --input definitions/pipeline_definition.xlsx --force-all`

### Build Staleness Check

At startup, `run_pipeline.py` compares the modification time of the Excel definition against `generated/build_manifest.json`. If the definition is newer than the last build, a warning is emitted — a reminder to rebuild before classifying.

## Troubleshooting

| Problem | Solution |
|---------|----------|
| `Module X not registered` | Run `build_pipeline.py build --force X` |
| Stale build warning at startup | Definition Excel is newer than last build — run `build_pipeline.py build` |
| L1 codes in primary_code columns | Regenerate with `--force-all`; add L2 descriptions to taxonomy sheet |
| Truncated JSON responses | Increase `max_tokens`; reduce `batch_size` |
| Rate limit errors | Reduce `concurrency` |
| Azure VNet error | Check `AZURE_API_BASE` in `.env` |
| `No batches created — 0 records` | Bad-UIDs file excluded everything — delete it and the checkpoint |
| Sentinel auto-detected wrong | Use `--sentinel module:field_name` |
| Enum values being blanked | Expected — pipeline normalises to lowercase allowed values |
| Blank description columns | Run `scripts/diagnose_and_fix_descriptions.py` to identify cause |
| Hallucinated evidence | Check `*_grounded` columns; strengthen verbatim prompts; rebuild with `--force-all` |
